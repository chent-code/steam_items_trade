# Skin Index — 挂刀比例策略分层回测

按「折扣最低前 10 / 20 / 50 名」构建四个指数，与全品种基准和分桶随机对照比较，检验挂刀比例策略是否有超额收益。

## 目录

```
skin-index/
  schema.sql            表结构
  config.example.json   配置模板（复制为 config.json）
  snapshot.py           每日快照采集（多数据源适配器）
  fetch_steam_history.py Steam 官方历史成交拉取（回填 1 号指数）
  backtest.py           指数构建 + 回测 + 归因 + 报告
  make_fake_data.py     合成数据生成器（先验证引擎，再接真数据）
  universe.txt          品种清单（market_hash_name，每行一个）
```

## 先跑通引擎（不需要任何 API key）

```bash
python make_fake_data.py --db test.db --alpha 0.4     # 注入"价差会收敛"的效应
python backtest.py --db test.db --out reports/alpha04
python make_fake_data.py --db test0.db --alpha 0.0    # 无效应的零假设
python backtest.py --db test0.db --out reports/alpha00
```

**判定引擎是否可信**：`alpha 0.4` 的 top-20 相对随机对照应显著为正；`alpha 0.0` 应约等于 0。
两者都对，引擎就是好的，剩下的只是接真数据。

## 数据现实（先读这段，决定走哪条路）

回测需要两类数据，可得性完全不同：

| 数据 | 用途 | 能否回填历史 |
|---|---|---|
| Steam 官方成交（价格+数量，按天） | 1 号指数、结果验证 | **能**，官方 pricehistory 接口，需要你自己的 steamLoginSecure cookie |
| BUFF/悠悠 在售价 + Steam 求购价（含挂单量） | 2/3/4 号的**信号** | **基本不能**。Steam 从未发布过历史求购价；聚合站（csqaq 等）有自己的快照存档但要 API key |
| BUFF/悠悠 历史成交明细 | 结果侧的真成交价 | 部分能（BUFF bill_order），爬取慢 |

**所以路径只有两条**：

- **路径 A（立刻有 2/3/4 号）**：买 csqaq 或 cs2.sh 的 API，用它们的存档回填信号 → 直接回测过去。成本是钱，风险是"存档里的 bid 快照粒度/口径未知"。
- **路径 B（零成本，等 8–12 周）**：从今天起每天跑 `snapshot.py`，前向攒数据。**这是无前提、保证能走通的路**，且因为 7 天保护期是强制的，你的 cohort 天然对齐。

**推荐 B 为主、A 为辅**：今天就把快照跑起来（哪怕先用 `--source manual` 手工录入挂刀插件里看到的数字），8 周后就有 8 个干净的 cohort；同时去买聚合站 API 的话，历史段用 A 回填、前向段用 B 无缝衔接。

## 每日快照（路径 B）

```bash
cp config.example.json config.json   # 填 cookie / key
python snapshot.py --source buff  --config config.json    # BUFF 列表页：在售价 + steam_buy_max
python snapshot.py --source cs2sh --config config.json    # 若有 key：buff+steam 双边 ask/bid/挂单量
python snapshot.py --source manual --file today.csv       # 手工/插件导出的 CSV，兜底，永远可用
```

`--source manual` 的 CSV 列：`item,platform,ask,ask_vol,bid,bid_vol,vol24`（platform ∈ buff/uuyp/steam）。
挂刀插件每天截一次图导出来，就能喂进引擎——**这条路径没有任何外部依赖**。

建议：固定每天同一时间（如 21:00）跑一次，crontab/任务计划程序皆可。

## 回测

```bash
python backtest.py --db skin.db --config config.json --out reports/run01 --index1 quote
```

- `--index1 quote`：用快照里的 ask→ask 变化（默认，数据要求最低）
- `--index1 sales`：用 steam_sales 表的 成交量×成交价 加权（回填后可用，这就是你说的"成交量×单价"加权）

输出到 `--out` 目录：`summary.md`（结论）、`per_rebalance.csv`（每期）、`per_name.csv`（每名）。

## 方法论规则（写死在引擎里，别绕过）

1. **Point-in-time**：T 日的排名只用 T 日及以前的数据。
2. **幸存者处理**：入选后无论中途是否跌出条件，一律持有到 T+7 记完整收益，不许中途剔除。
3. **固定周几调仓**（默认周一），cohort 互不重叠，t 检验才干净。
4. **权重**：top-N 内等权（薄订单簿吃不进量），换手率只做**过滤**不做权重；单名权重上限默认 20%。
5. **三个退出口径都报**：平台在售价（乐观）/ 平台求购价（保守，吃价差）/ Steam 求购价×0.85（Steam 退出）。**主指标先验指定为"平台求购价退出"**，写死，不许回头挑最好看的那个。
6. **入场成本**：按在售价计；若 ask_vol 小于你的量，真实成本会沿阶梯上移——当前快照只存一档，量 > ask_vol 的名字会被打上 `thin_top` 标记。
7. **主指标 = top-N vs 分桶随机对照**（同价位分十分位、桶内随机抽 N 个）。top-N vs 大盘只作次要参考。
8. **先验指定 N=20 为主**，10/50 是稳健性检查。不许跑完全部再看哪个最漂亮。
9. **折扣比值（Δratio）归因**：若超额收益与比值向锚回归的幅度同向，机制是收敛；若超额与 Δratio 无关，你赚的是 beta。引擎每个 cohort 都输出 Δratio，最后给相关系数。
10. **结论门槛**：< 26 个 cohort（约 6 个月）只能叫"冒烟测试"，不能叫"验证"。报告里会自动标注当前 cohort 数。

## 已知局限

- 快照只存买一/卖一档，没有全阶梯 → 大仓位入场成本会低估。
- BUFF API 字段可能变动，脚本会把第一页原始 JSON 存到 `debug_buff_page1.json`，**第一次跑完务必人工核对字段名**。
- 悠悠有品无公开 API，adapter 留了桩；可行做法：抓挂刀插件发出的 XHR 请求，把响应转成 manual CSV 喂进来。
- Steam pricehistory 的价格按你账号币种返回，注意统一成 CNY 再算比值。
